## 环境保护与实际操作

1. 读取 GitHub `plugin/` 和兼容性文档。原工作目录只有此前生成的本地资源，不是 Git 仓库；从远程 `main` 建立本地仓库与 `codex/desktop-rc3-compat` 分支，保留原本地资源。
2. 在用户明确授权当前环境测试后，仅操作现有 `desktop` profile。用户明确确认所有任务已结束后才重启。
3. 私有目录 `.acceptance/backup-current-20261028/` 中对七个相关配置文件作字节备份：profile 清单、锁文件、workspace、patch、生成配置，以及桌面选择/设置文件。备份没有打印内容、没有提交 Git。凭据存储未打开、复制或修改。
4. 保留原正确的 `- insert:` Cordis 补丁格式；补充 package exports、显式无服务依赖声明，以及由 Cordis `ctx.effect` 管理的启动/停止证据。核对的是桌面实际携带的 loader 与 Cordis API。
5. 经桌面内置 CLI 安装最小包。宿主实际记录 started；正常退出记录 stopped；重新启动再次记录 started。卸载后原插件清单恢复，DSH 再次启动正常。
6. 通过安全关后才编写/安装窗口实验版。窗口层使用官方 Neutralino 6.9.0 和本地未修改的 KuroWhale 包；没有重装 DSH，没有引入旧 DSH 前端。
7. 窗口未通过可见性检查后，没有继续安装后续版本。立即卸载实验版并核对原环境。随后用现有模型完成不调用工具的回复测试，最后再次重启验证恢复。

部分必要的正常退出操作通过桌面 UI 进行。前台焦点冲突使菜单操作不稳定时，在用户已确认空闲并授权重启的范围内，对路径精确匹配的 DSH 主进程树作定向重启。**这种重启不冒充正常退出测试。**未定向终止其他应用。

## 失败分析与下一步代码

目前能证实的是：DSH 宿主可加载；Native IPC、WebView2 页面代码和 atlas 解码可运行；**画布绘制与 Windows 屏幕可见性之间仍有缺口**。根因尚未查明。不能仅凭这些现象断言是 DPI、GPU、窗口位置或透明参数中的某一个。

下一步应只定位这个缺口，不先增加功能：

1. 在 `plugin/native/index.html` 增加独立的纯色/已知不透明测试块和 canvas 像素边界诊断，并核对页面/CSS/设备像素尺寸；不修改角色美术。
2. 在 `plugin/overlay.js` 记录自己创建窗口的原生可见性、位置/尺寸和就绪阶段，确认不是仅连接到了可绘制但不可见的页面。不要读取 DSH 的认证信息或给整个桌面应用开放调试端口。
3. 对照实际屏幕截图与用户目视结果。保留 `rendererReady`（通讯就绪）与 `visibilityVerified`（视觉验收）两个概念，后者不能由前者自动置真。
4. 可见性通过后，再做九状态录屏、拖动/缩放/隐藏与重新启动；最后做真实工具与审批、两会话优先级及性能采样。
